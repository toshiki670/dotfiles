# 成果物を変更するときは、足す前に既存を直す

コード・文書・設定・skill・memory など、どの成果物を変更するときも、新しく足す前に既存を見直す。

## 順番

1. **既存を探す。** 新しい関数・ファイル・節・記録を作る前に、同じ役目・同じ話のものが既に無いか確かめる。
2. **既存を直す。** 重なるものはまとめ、誤り・古くなったものは書き換えるか消す。
3. **それでも足りないときだけ足す。**

## まとめるかどうか

Common Closure Principle で決める。同じ理由で一緒に変わるものだけをまとめ、見た目が同じでも変わる理由が違うもの（accidental duplication）は分けたままにする。まとめ損ねると Shotgun Surgery、まとめすぎると Divergent Change になる。

一緒に変わるかは change coupling で確かめる。今回の変更で同じ直しを2箇所以上に入れることになったか、git の履歴で同じコミットに繰り返し現れてきたかを見る。

## 範囲

見つけたものが、今回の依頼・チケット・与えられた役割の範囲に入るかで扱いを分ける。

- **範囲内:** その場で直す。
- **範囲外:** 勝手に直さず、黙って見送りもしない。何を・なぜ直すべきかをユーザーへ伝え、Issue にするかを委ねる。

## 渡す前

変更をひと区切りつけて渡す前（PR を出す前など）に、diff とその変更を頼んだ文を `debt-audit` agent へ渡し、最終監査を掛ける。編集のたびには呼ばない。
