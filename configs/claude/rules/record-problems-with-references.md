# 指摘や自分で見つけた問題を memory へ残すとき

指摘への答えは、まず作業そのものを直すこと。memory への記録は、その後で次の作業にも効く教訓が残ったときだけ行う。組み込みの Memory 指示が記録を促す場面でも、この rule の条件と順番を先に当てる。

## 書くかどうか

次の両方に当たるときだけ書く。当たらなければ書かない。

- **次の作業にも当てはまる。** 今回の作業だけの直し（この PR のこの行、このファイルの書き方）は、直せば済むので書かない。
- **原因と直し方が分かっている。** 指摘を受けたその場では書かない。直して確かめた後か、会話の終わりで考えが固まってから書く。同じ会話の中で考えが変わったら、先に書いたものを直す。

ユーザーが明示的に「覚えて」と頼んだときは、この2つを問わない。順番（下）は省かない。

## 順番

1. **既存を探す。** 同じ話・近い話の記録が無いか、memory の索引と本文を確かめる。
2. **既存を直す。** 重なるものはまとめ、誤り・古くなったものは書き換えるか消す。
3. **それでも足りないときだけ足す。**

足すより直すほうを先にする。同じ話を別のファイルへ分けない。

作業中に、既存の記録が古い・誤り・ほかの記録に取って代わられたと分かったときも、その場で直すか消す。

## 書く中身

- **当てはまる範囲を書く。** どの場面で効き、どの場面では効かないか。一つの場面の指摘を、関係の薄い作業まで広げない。範囲が近い記録が既にあるなら、新しく足さずにその範囲を広げる。
- **指摘した人の言葉と、自分の推測を分ける。** 理由づけなど自分が補ったものは、推測だと分かる書き方にする（「〜と推測」「理由は聞いていない」など）。
- **`**How to apply:**` には、次に同じ場面で自分が取る行動を書く。** 「この決まりを適用先のファイル側へ書いておけ」という形にしない。そう書くと、その後に触ったファイルへ、その決まり自体を説明する文言が入る。

```markdown
**How to apply:** PR を出す前に、受け入れ条件と実際に書いた場所を1件ずつ対応させて確かめる。
```

## 参照リンク

その作業の Issue・チケット・PR・チャットなど、後から辿り直せるリンクがあるときは、本文の末尾に `**参照:**` の行を足す。無いときは行ごと書かない。

```markdown
**参照:** toshiki670/dotfiles#738, PR #737
```

実際にその作業で触れたものだけを書く。心当たりを推測で埋めない。

## 例外

機密情報や、他では再現しない一時的な文脈は、そのまま memory へ書き写さない。
