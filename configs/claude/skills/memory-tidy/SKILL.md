# memory-tidy — Auto memory の棚卸し

プロジェクトの **Auto memory**（`~/.claude/projects/<project-slug>/memory/`、`MEMORY.md` 索引 ＋ 1 ファイル = 1 事実の fact ファイル群）を棚卸しし、陳腐化・重複・索引ズレを解消する。

## 方針（厳守）

- **将来の有用性で残す/消すを判断する**。陳腐化＝即削除ではない。陳腐だが今後も役立つものは事実だけ更新するか恒久的な核へトリムして残す。消化済み・他メモリやコード/git で完全に代替できるものだけを削除候補にする。
- **「正しいか」と「今後も参照され得るか」は別軸**。前者は3で実態照合する。後者は自動計測できない（読了ログは存在せず、読まずに内在化される知識もある）ので、frontmatter に最終利用日時のような欄は設けない。日付は本文中に明記する運用（例:「2026-07-05, PR#585 で…」）に一本化し、内容を更新したときだけ書く。**以降「更新日」は本文中に現れる最新の明記日付を指す。明記日付が無いメモリは「更新日不明」として扱い、それ自体を陳腐化の根拠にしない**（古くから触っていない安定したメモリと、単に日付を書いていないだけのメモリを区別できないため）。
- **未確認の事実を断言しない**（report-facts-only）。陳腐化の指摘は必ず実態照合してから報告する。確認前は「〜の懸念がある」と書く。MCP/外部サイトが未接続・未到達で照合できない場合も同様に「未検証」と明記し、断定しない。
- **不可逆操作は必ず確認する**。memory ディレクトリは **git 管理外**で、削除・上書きは取り消せない。
- 安全な修正は自動適用してよいが、削除・統合（不可逆）は一覧提示しユーザー承認後にのみ実行する。

## 手順

### 1. 対象を読む

- 現在のプロジェクトの memory ディレクトリを特定する（cwd の絶対パスを `/` → `-` に置換した slug の `~/.claude/projects/<slug>/memory/`）。
- `MEMORY.md`（索引）と全 fact ファイルを読む。
- **8 の階層化（カテゴリ別サブディレクトリ＋サブ索引）が既に行われていないか確認する。** 行われていれば、以降の手順（2・7 含む）は「トップレベルの `MEMORY.md` はカテゴリ単位」「各サブ索引は fact 単位」という2段構成を前提に読み替える。フラットな1段構成だと誤認してカテゴリ化を元へ戻さない。

### 2. 整合性チェック（内部のみ・安価）

- **索引 ↔ ファイル**: 索引に行が無いファイル（孤立）、索引にあるがファイルが無い（欠落）。**8 で階層化済みの場合はカテゴリのサブ索引を単位に見る**（fact を直接トップレベル `MEMORY.md` と突き合わせて「孤立」と誤検出しない）。
- **壊れた `[[link]]`**: 指す先の `name` が存在しないリンク。
- **壊れた設定ファイル参照**: 本文が `~/.claude/rules/<name>.md` のようなパスで rule・skill を名指しているとき、その実体が実在するか・種別（rule か skill か）が合っているかを確認する。`[[link]]` 形式ではないので上のチェックでは捕まらない。
- **frontmatter の妥当性**: `name` / `description` / `metadata.type`（user / feedback / project / reference）の有無。
- **`MEMORY.md` の読み込み上限（目安ではなく実際の切り捨てライン）**: 先頭 200 行 or 25KB（どちらか早い方）を超えた分は**セッション開始時に一切読み込まれない**（Claude Code 公式仕様）。超過は「見た目が長い」程度の問題ではなく、超過分のメモリが今後のセッションから実質的に消えている状態＝最優先で是正する。`wc -l` / `wc -c` で実測して確認する。
- **索引の1行あたりの長さ**: 目安 150 字以内か。索引行が本文の要約でなく全文複製になっている（＝本来ファイル側にしかないはずの詳細が索引に漏れ出している）のは、索引が「索引」の役目を外れているサイン。
- **重複・内容のかぶり**: 同じ事実が複数ファイルに分散していないか。

### 3. 陳腐化の能動検証

各メモリの主張を実態と照合する。事実として正しいかどうかだけを見る（今後も参照され得るかは 4 で別途扱う）:

- `git log` / リポジトリ状態、参照している GitHub Issue・PR を `gh issue view` 等で状態確認（CLOSED / merged か）。
- **GitHub 以外のチケット系**（Linear / Jira / Notion 等）を参照するメモリは、対応する MCP ツールで現在の状態を確認する。
- **外部サイトの記載を根拠にしたメモリ**（バージョン・公式ドキュメントの仕様等）は WebFetch/WebSearch で再取得し突き合わせる。
- メモリが名指しするファイル・関数・フラグ・パス・バージョンの実在確認。
- 「完了済みを進行中として書いている」「解決済みの未確定事項」「実態と異なる実装詳細」を検出する。
- **MCP 未接続・未認証や到達不能で確認できない場合は「不明」として扱う。** 確認できなかったことを「陳腐化なし」の根拠にしない（report-facts-only）。

### 4. 有用性の判定（正確性 ≠ 参照され得るか）

3 で事実確認した上で、**「今後も参照され得るか」を type ごとに判定する**:

| type | 陳腐化の起点 | 判定材料 |
|---|---|---|
| `project` | 初期タスク/構想の完了 | 参照する Issue/PR が閉じ、追跡すべき未完項目も残っていなければ圧縮/削除候補 |
| `feedback` | 対象の状況・ツール自体の消滅 | 更新日の古さでは判断しない（低頻度発火が正常）。対象の状況/ツールがまだ存在するかだけを見る |
| `reference` | 対象ツール/コマンド/バージョンの引退 | 3 の実在確認（ファイル/コマンド/バージョンが実際に無くなっているか）が主判定材料 |
| `user` | ユーザーの役割/前提の変化 | 明示的な自己申告がない限り自動では削除しない |

被リンク数（`[[link]]`が0件）は `project` / `reference` の判定に使ってよいが、**単独のトリガーにしない**。この2 type でも被リンク0は普通に起きる（`feedback` と同様、単独で効く孤立したメモリは健全にありうる）ため、3 で陳腐化が実際に判明した場合の**補強材料**としてのみ使う。`feedback` はそもそも対象外（強いルールほど他から参照されず単独で効くのが正常）。

事実確認は通ったが上記の弱いシグナル（project 完了・reference 孤立）が重なる中間層は、削除候補にする前にユーザーへ一言確認する（例:「最近実際に効いた場面はありますか」）。**更新日の古さ単体をトリガーにしない**（`feedback` を毎回引っかけてしまう）。

各メモリの最終判定には必ず理由を添える:

- **陳腐だが有用** → 事実部分のみ更新、または恒久的な核へトリム。
- **消化済み / 冗長**（他メモリやコード/git で完全に代替可能） → 削除候補。
- **判断つかず** → ユーザーに確認。

### 5. feedback を抽象度で束ねる（`feedback` のみ）

2 の重複検出は「同じ事実が複数ファイルに分散している」字面のかぶりを見る。ここで扱うのは**違う出来事が同じ本質を持つ**ケースで、字面は一致しない。

feedback は指摘を受けた時点で記録されるが、そのとき走る「既存メモリに同じ論点があるか」の検索は**具体のレベル**で行われる。表層が違えば同じ本質でも別件として通り、毎回「初出」として新しいファイルになる。ここはその取りこぼしをまとめて回収する場。**目的は索引を短くすることではなく、同じ問題を1か所に集めて次に発火しやすくすること。**

#### 5-1 誤りの形を書き出す

feedback 各件について「何を誤ったか」を1文にする。**対象ツール・トピック・ファイル名・コマンド名を含めずに書く。** 含めたまま読むと表層のまとまり（バージョン管理系・文書系・設定系…）になり、索引を眺めれば分かる以上のものは出ない。

まず `description` だけを通しで読んで書き出す。**本文を精読するのは、5-2 で候補に入ったものだけ。** 件数が増えるほどこの差が効く。

**誤りの形が書き出せないものは、束ねる対象から外す。** feedback には、失敗の記録ではなく事実・許可・好みを述べたもの（「この場面ではこうしてよい」「この表記で揃える」等）も混じる。無理に「何を誤ったか」へ言い換えると、実際には共有していない軸で束ねてしまう。

#### 5-2 同じ形のものを束ねる

書き出した1文どうしを突き合わせ、同じ形のものを集める。この段階で候補に入ったクラスタだけ、メンバーの本文を読む。

#### 5-3 段1: 形を決める

クラスタの**メンバー同士を比べる**。誤りの形が違えば別クラスタなので、以降は比べない。形が同じものについて、次の2軸で結末が決まる。

| 発火の瞬間 | 対処行動 | 結末 |
|---|---|---|
| 同じ | 同じ | **統合** |
| 同じ | 違う | **階層化** |
| 違う | 同じ | **階層化** |
| 違う | 違う | **階層化** |

**発火の瞬間**＝そのメモリを適用すべき場面。同じ徳を説いていても適用の瞬間が違えば別物として扱う（片方を守っていても、もう片方は防げない関係になる）。ここを見ないと、抽象度の近いものが1つの大きな塊に潰れ、実際には発火しない親ができる。

だから**瞬間が違えば、対処行動が同じでも統合しない**。共通の行動は親へ、各々の瞬間は子へ置く形が階層化そのもので、1ファイルに瞬間を並べるとやがて description が全部を名指せなくなり、発火しない瞬間が出る。

- **統合** — 1ファイルへ畳む。本文は抽象の記述にし、各インシデントは1行の一覧へ落とす（下記）。
- **階層化** — 親は共通の軸だけを持ち、個別のインシデントは持たない。子は自分の発火の瞬間と記録を保持したまま、親を `[[link]]` で指す。
- 形は違うが片方が他方の精緻化になっている等の**弱い関連**は、ファイルを動かさず `[[link]]` を足すだけに留める。

統合後・親への集約後は、インシデントを次の形へ畳む:

```markdown
**繰り返し:**

1. <日付> <PR/Issue 等の参照> — <何を誤ったか>
2. <日付> <参照> — <何を誤ったか>
```

#### 5-4 段2: 置き場所を決める

段1 が出したユニット（統合したファイル・新設した親）ごとに、**その中身の性質**を見る。メンバー同士の比較ではないので、段1 の表とは分ける。

- **常時守るべき制約** → **rule 昇格の候補**として出力に挙げる。畳んだ反復の一覧がそのまま根拠になる。挙げても memory 側は消さない。
- **特定の場面でだけ効く** → memory のまま。

rule か skill か・どの階層へ置くかまではここで決めない。**候補として挙げるところで止め**、配置は Claude Code 設定の配置判定を担う skill へ渡す。ここで先まで決めると、配置側の条件分岐と矛盾する。

#### 5-5 提案の前に、却下済みを除く

「見送り」「保留」「再提案しない」と記録されたメモリを先に検索する。該当するクラスタは提案に載せない。載せる場合は「前回保留」と明示する。

ユーザーが却下したクラスタは、**その場で却下の記録を書く**。書かなければ、次回の棚卸しで同じクラスタを初回として再提案する。

#### 5-6 提案は絞って出す

1回の承認で捌ける数に収める。順序は、**反復回数の多いクラスタを先に**（繰り返し起きている＝実害が大きい）、同数なら可逆な順（リンク追加 → 親の新設 → 統合）。載せなかったクラスタは件数と理由を明示する。黙って切ると「全部見た」と読める。

#### 守ること

- **抽象は具体の置き換えではない。** インシデント記録（日付・参照・何を誤ったか）を、抽象化を理由に失わせない。担保はファイルを分けたまま残すことではなく、**統合先へ一覧として畳むこと**。反復回数が rule 昇格の根拠であり、削ると次回また初出に見える。
- **既存の rule・skill と同義でしかない親を作らない。** そのクラスタは既存の抽象の実例なので、具体側の本文に「どの rule の実例か」を1行足すだけでよい。rule 側が実例不足で効いていないなら、rule の強化を 5-4 の候補として挙げる。
- **クラスタ内に既に親がいるなら、新設せず子を足す。** メンバーの1つが共通の軸だけを持ち他から `[[link]]` で指されていれば、それは前回の棚卸しが作った親。結末は「親の新設」ではなく、まだ繋がっていないメンバーからのリンク追加になる。親と子は同じ形のまま残るので、次の実行でも同じクラスタとして再検出される — ここを見ないと、存在する親を毎回提案する。
- **frontmatter を拡張しない。** 親子関係は本文の `[[link]]` だけで表す。
- `feedback` 以外の type へ広げない。

### 6. 適用

- **自動適用（安全）**: `MEMORY.md` 索引の同期、孤立解消 / 欠落除去、壊れたリンク修正、事実の更新 / トリム、5 のリンク追加。
- **承認後に実行（不可逆）**: ファイル削除、メモリの統合、親の新設。実行前に「対象・理由・代替の所在」を一覧で提示する。

### 7. 索引同期

- `MEMORY.md` を実態に合わせる。1 メモリ = 1 行、目安 150 字以内（`- [Title](file.md) — hook`）。メモリ本文は索引に書かない。**8 で階層化済みの場合はカテゴリ単位に読み替える**（トップレベル `MEMORY.md` は1カテゴリ=1行、fact 単位の1行ルールは各サブ索引側に適用する。フラット構成へ戻さない）。

### 8. 索引が肥大化した場合の再編（閾値に近づいた時のみ）

- **発火の判定は 5・7 を適用した後に再測定した値で行う。** 統合でファイルが減り、150 字トリムで行が縮んだ結果、上限に余裕が戻っていることがある。古い測定値のまま再編へ進まない。
- 再測定してもなお `MEMORY.md` が読み込み上限（200 行 / 25KB）に近づいている場合**だけ**、カテゴリ単位の階層化を検討する。余裕がある間に先回りして再編しない（過剰設計）。
- 再編方法: fact ファイルをテーマ別のサブディレクトリへ束ね、各サブディレクトリに短いサブ索引（例: `<category>/INDEX.md`）を置く。トップレベルの `MEMORY.md` は個々の fact でなく**カテゴリ単位で1行**だけを持ち、そのサブ索引を指す。fact 数が増えてもカテゴリ数はずっと緩やかにしか増えないため、`MEMORY.md` 自体の肥大化を先送りできる。
- **5 で親を新設している場合は、テーマを別途考案せずその親をカテゴリの単位に使う。** ただし親子関係は `[[link]]` が正で、ディレクトリはその写しに過ぎない。1つの子が複数の親から指されているときは、どちらか一方のディレクトリへ置き、もう一方のリンクはそのまま残す。
- fact ファイル自体の内容・命名規則・1ファイル=1事実の原則は変えない。索引の階層を一段増やすだけ。

## 出力

1. 検出結果（メモリ別に: 状態 / 判定 / 理由。MCP/外部サイトで未検証だった項目はその旨を明記）。
2. 自動適用した安全な修正の一覧。
3. 承認待ちの不可逆操作（削除・統合・親の新設）の一覧と推奨。
4. **rule 昇格の候補**（5-4）。クラスタ名・反復回数・根拠となるインシデント一覧を添える。配置先は決めない。
5. **提案から外したクラスタ**（5-5 の却下済み / 5-6 の上限超過）を件数と理由付きで。
6. 利用実感の確認が必要な項目（あれば、理由付きで）。
