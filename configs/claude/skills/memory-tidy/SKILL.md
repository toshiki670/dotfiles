# memory-tidy — Auto memory の棚卸し

プロジェクトの **Auto memory**（`~/.claude/projects/<project-slug>/memory/`、`MEMORY.md` 索引 ＋ 1 ファイル = 1 事実の fact ファイル群）を棚卸しし、陳腐化・重複・索引ズレを解消する。

## 方針

- **memory は時間で古びない事実だけを持つ。** `type: feedback` は memory の外へ搬出する（手順3）。記録そのものの形は `~/.claude/rules/record-problems-with-references.md` が定める。
- **陳腐化・重複・不要の判定は自分で行わず、`debt-audit` agent へ渡す**（手順4）。この skill が持つのは、memory 固有の材料の集め方と、返ってきた分類をどう処置するか。
- **分類がそのまま削除にはならない**。分類ごとの処置は手順5。
- **「正しいか」と「今後も参照され得るか」は別軸**。後者は自動計測できない（読了ログは存在せず、読まずに内在化される知識もある）ので、frontmatter に最終利用日時のような欄は設けない。日付は本文中に明記する運用（例:「2026-07-05, PR#585 で…」）に一本化し、内容を更新したときだけ書く。**明記日付が無いメモリは、それ自体を陳腐化の根拠にしない**（古くから触っていない安定したメモリと、単に日付を書いていないだけのメモリを区別できないため）。
- **日付が明記された観測は、その挙動を説明する仕組みが別にあるかで決める。** 仕組みのほうが挙動を説明しているなら、観測は仕組みから導ける例示なので落とす（出所は仕組みの側）。観測だけがその存在の証拠で、仕組みからは導けないなら、日付付きのまま残す。
- **書き換える前にスナップショットを取る**。memory ディレクトリは **git 管理外**なので、6 の手順で退避してから触る。
- **承認が要るのは、内容が消える操作だけ**（対象は 6 で列挙）。内容が残る操作は、誤っていても実行後の出力を読めばその場で気づけるので自動適用してよい。消える方は気づく契機が無い（無いものは思い出せず、次に効くはずだった場面は先になる）ため、スナップショットがあっても事前承認を課す。搬出（3）は内容が残る側だが、memory の読み込み経路からは外れる。承認は課さず、3-1 の判定を残す側へ倒すことで釣り合わせる。

## 手順

### 1. 対象を読む

- 現在のプロジェクトの memory ディレクトリを特定する（cwd の絶対パスを `/` → `-` に置換した slug の `~/.claude/projects/<slug>/memory/`）。
- `MEMORY.md`（索引）と全 fact ファイルを読む。
- **fact がサブディレクトリへ分かれていないか見る。** カテゴリ別に階層化されていることがある（フラットに保つ理由は 8）。ここでは分かれているかを確かめるだけで、**移動も索引の書き換えもしない**。フラットへ戻すのは 6 で退避を取った後。

### 2. 整合性チェック（内部のみ・安価）

- **索引 ↔ ファイル**: 索引に行が無いファイル（孤立）、索引にあるがファイルが無い（欠落）。
- **壊れた `[[link]]`**: 指す先の `name` が存在しないリンク。コードとして書かれた `[[…]]`（フェンス付きコードブロック・インラインコードスパンの中）はリンクではない。TOML の配列テーブルや正規表現の文字クラスと字面が一致するだけで、指す先を持たない。
- **壊れた設定ファイル参照**: 本文が `~/.claude/rules/<name>.md` のようなパスで rule・skill を名指しているとき、その実体が実在するか・種別（rule か skill か）が合っているかを確認する。`[[link]]` 形式ではないので上のチェックでは捕まらない。
- **frontmatter の妥当性**: `name` / `description` / `metadata.type`（user / feedback / project / reference）の有無。
- **`MEMORY.md` の読み込み上限（目安ではなく実際の切り捨てライン）**: 先頭 200 行 or 25KB（どちらか早い方）を超えた分は**セッション開始時に一切読み込まれない**（Claude Code 公式仕様）。超過は「見た目が長い」程度の問題ではなく、超過分のメモリが今後のセッションから実質的に消えている状態＝最優先で是正する。
  - **日本語の索引では 25KB が先に効く。行数だけを見ない。** 1行 200 バイト前後なら 126 行あたりで 25KB に達し、200 行には届かない。`wc -c` を主、`wc -l` を従として読む。
  - 計測対象は**読み込まれる内容だけ**。YAML frontmatter と block-level HTML コメントは読み込み前に除去され上限に数えられないので、それらがある場合は生ファイルの `wc` が過大計上になる。
- **索引の1行あたりの長さ**: 目安 150 字以内か。索引行が本文の要約でなく全文複製になっている（＝本来ファイル側にしかないはずの詳細が索引に漏れ出している）のは、索引が「索引」の役目を外れているサイン。

### 3. feedback を搬出する

組み込みの Memory 指示が `type: feedback` を作り続けるので、棚卸しのたびにここで memory の外へ出す。

**3 を全件終えてから 4 を始める。並行して起動しない。** 3-1 が `metadata.type` を付け替えるので、走らせたまま監査すると監査の最中に対象が変わる。付け替えたものは、この実行から監査の対象に入る。

途中で落ちても、残っている `type: feedback` から再開できる（3-3 が書き出しの成功を待って元を消すため）。

#### 3-1 公式の型に当たるものを残す

各ファイルについて、組み込みの Memory 指示が定める他の3つの型に当たるかを見る。

| 型 | 処置 |
|---|---|
| `user` | `metadata.type` を付け替えて memory に残す |
| `project` | 同上 |
| `reference` | 同上 |
| どれにも当たらない | 3-2 へ（搬出） |

迷ったら付け替えて残す。

**本文は書き換えない。** 付け替えるのは `metadata.type` だけ。時間で古びる書き方の是正は 5 が持つ。

#### 3-2 参照リンクを補う

搬出するファイルに `**参照:**` の行が無ければ足す（形は `~/.claude/rules/record-problems-with-references.md`）。

**本文に既に現れている Issue / PR 番号と URL だけを拾う。** 本文に無いものを、記録の時期や内容から推測して埋めない。ファイルパスや `[[link]]` は作業の参照ではないので拾わない（本文に残る）。

本文から1つも拾えなければ `**参照:** 不明` と書く。ここでの `不明` は「本文から特定できなかった」であり、`なし`（紐づく参照がそもそも存在しない）とは別。書いた本人がいない過去分について `なし` は断定できない。

#### 3-3 書き出してから消す

- 置き場所は `~/Claude/feedback/<slug>/`。`<slug>` は `~/.claude/projects/<slug>/` と同じもの。
- ファイル名は `<originSessionId>_<搬出元のファイル名>`。frontmatter に `originSessionId` が無ければ `unknown_<搬出元のファイル名>`。
- frontmatter ごと持っていく。`originSessionId` と `modified` は、後から原因を調べるときの手がかりになる。
- **順序を逆にしない。** 書き出す → 内容が一致することを確かめる → `MEMORY.md` から索引行を外す → memory 側を `trash` へ送る。元を消した後に索引行が残ると、次の実行で 2 が「欠落」と判定し、承認待ちになって自動では再開できない。
- 索引行の除去は、内容が `~/Claude/feedback/` に残っているので 6 の承認は要らない。
- 書き出し先に同じ名前のファイル（連番を足したものを含む）が既にあるなら、**内容を照合してから決める。** 同名であることは、前回の実行が元を消す前に落ちた跡であることを意味しない。
  - 一致する → 前回の跡なので、書き出しを省いて元を消す。
  - 一致しない → **既存には触らない。** 末尾に連番を足した別名で書き出す。既にあるほうは、搬出された後に書き足された記録かもしれない。
- 別名で書き出したものは、出力の「搬出の結果」へ件数と名前を出す。黙って2ファイルになると、同じ問題の記録が別物として扱われる。

同じ状態に2回走らせても、2回目は `type: feedback` が残っていないので何も起きない。

### 4. 材料を集めて `debt-audit` へ渡す

**起動する前に、3 が全件終わっていることを確かめる。** memory ディレクトリに `type: feedback` が1件でも残っているなら 3 が途中なので、監査を起動せず 3 を終わらせる。

対象は、この時点で memory ディレクトリに残っている fact ファイル全件。3-1 で `metadata.type` を付け替えたものも含む。

**ファイルの絶対パスを1行1件で列挙して渡す。** 件数・ファイル名の接頭辞・「〜以外」といった絞り込み条件では渡さない。あわせて「列挙したパスが対象の全部である。ディレクトリを走査して数え直さない。列挙と実際に見えているものが食い違うなら、別の手がかりで読み替えず、判定を始めずに呼び出し元へ返す」と伝える。対象を選ぶ手がかりはファイル名の側にも残っているので、伝えないと読み替えが起きる。

各メモリの主張を実態と照合し、照合結果を添えて渡す。分類そのものはこの skill では出さない。

- **この棚卸しを頼んだ文（そのまま）。** debt-audit は依頼文が無いと判定を始めない。`/memory-tidy` だけで起動したならそう伝え、対象の絞り込みや気になっている点を添えられていればそのまま渡す。
- `git log` / リポジトリ状態、参照している GitHub Issue・PR を `gh issue view` 等で状態確認（CLOSED / merged か、追跡すべき未完項目が残っていないか）。
- **GitHub 以外のチケット系**（Linear / Jira / Notion 等）を参照するメモリは、対応する MCP ツールで現在の状態を確認する。
- **外部サイトの記載を根拠にしたメモリ**（バージョン・公式ドキュメントの仕様等）は WebFetch/WebSearch で再取得し突き合わせる。
- メモリが名指しするファイル・関数・フラグ・パス・バージョンの実在確認。
- **その主張が、いつ測っても同じ事実か、いまの状態を持つものか。** debt-audit は Outdated / Trivial を「この先も編集され続けるもの」か「一度書いたら書き換えない記録」かで分けるので、この区別が無いと判定が出ない。
- 同じ事実を持っていそうな他メモリ・コード・git 履歴を、出所の候補として一緒に渡す。

**被リンク0**は `project` / `reference` では普通に起きるので、他の照合結果と重なったときだけ補強として添える。`user` は明示的な自己申告がない限り、削除の材料を渡さない。

### 5. 返ってきた分類を処置に落とす

**渡したパスの一覧と、返ってきた判定の対象を突き合わせる。** 欠けがあれば、欠けたぶんを 4 へ渡し直し、判定が揃ってから処置へ入る。渡していないパスの判定が混ざっていれば、対象が読み替えられているので、その回の判定を採らず 4 からやり直す。どちらも、食い違いを出力へ書いて次へ進まない。

**表の行で打ち切らない。** 表の下の2つは、返ってきた分類に関わらず効く。

| debt-audit の返答 | 処置 |
|---|---|
| Outdated だが今後も役立つ | 恒久的な核へトリムする。時間で変わる値が主張の中心なら、いまの値へ差し替えず、値を持たない書き方へ書き換える |
| Redundant / Trivial | 削除候補（承認は 6）。弱いシグナルだけで落ちたものは実行前にユーザーへ一言確認する（例:「最近実際に効いた場面はありますか」） |
| 該当なし | そのまま残す |

**日付が明記された観測は、方針の基準（その挙動を説明する仕組みが別にあるか）で残すか落とすかを決める。** debt-audit が Outdated と返したかどうかでは決めない。

**4 で「いまの状態を持つもの」と分かったメモリは、分類が付かなくても処置する。** 今この瞬間は正しいので debt-audit は「該当なし」を返すが、次の棚卸しでも同じ書き換えが要る。状態を持たない書き方へ書き換え、書き換えると何も残らないなら削除候補（承認は 6）へ回す。状態そのものは参照リンク先が持つ。

表に無い分類が返ったら、削除へ直結させず改善候補として報告する。

### 6. 適用

書き換えが1つでもあるなら、**最初の書き込みの前に** memory ディレクトリを丸ごと退避する。退避先は memory ディレクトリの**外**（`~/.claude/projects/<slug>/memory-backup-<YYYYMMDD-HHMMSS>/`）— 中へ置くと 1 で fact ファイルとして読み込んでしまう。

作業を終えたら退避を zip へ固め、zip と退避ディレクトリの両方を `trash` でゴミ箱へ送る。作業中に問題が起きれば退避から戻せ、終わった後に気づけばゴミ箱から戻せる。出力に zip 名を書く。

- **自動適用**: `MEMORY.md` 索引の同期・孤立解消、壊れたリンク修正、書き方の書き換え / トリム、3 の搬出・`metadata.type` の付け替え・索引行の除去、1 で見つかったサブディレクトリのフラット化。
- **承認後に実行**: ファイル削除と、欠落した索引行の除去。後者も、本体が失われたメモリについては索引行が最後の痕跡なので、消す前に見せる。実行前に「対象・理由・代替の所在」を一覧で提示する。

### 7. 索引同期

- `MEMORY.md` を実態に合わせる。1 メモリ = 1 行、目安 150 字以内（`- [Title](file.md) — hook`）。メモリ本文は索引に書かない。
- **2 で見つけた欠落の行は、ここで消さない。** 実態へ合わせる流れで消せてしまうが、承認が要る操作なので 6 に従う。

### 8. 索引が上限に近づいた場合

- **判定は 3・5・7 を適用した後に再測定した値で行う。** 搬出でファイルが減りトリムで行が縮むので、古い測定値のまま次の手へ進まない。
- 詰める順: **1 メモリ = 1 行まで詰める（7）→ 分類の付いたものを落とす（5）**。ここまでやってなお上限に届くなら、削除候補の線引きをどこまで下げるかをユーザーへ相談する。
- **サブディレクトリによる階層化はしない。** セッション開始時に読み込まれるのは `MEMORY.md` だけで、fact ファイルは必要になったときファイルツールで読む。トップレベルから個々の fact への行を外すと、そのファイルを読む契機が、文書化された仕組みとしては残らない。索引は1メモリ=1行のフラットな形を保つ。

## 出力

1. 検出結果（メモリ別に: 状態 / 判定 / 理由。MCP/外部サイトで未検証だった項目はその旨を明記）。
2. **搬出の結果**: 搬出した件数と書き出し先、別名で書き出した件数と名前、`metadata.type` を付け替えて残した件数と新しい型、書き出しに失敗した件数と対象。失敗したものは memory に残っているので、次の実行で再開すると明記する。
3. 自動適用した修正の一覧と、退避を固めた zip 名（戻す手段の所在）。
4. 承認待ちの操作（ファイル削除・欠落した索引行の除去）の一覧と推奨。
5. 利用実感の確認が必要な項目（あれば、理由付きで）。
