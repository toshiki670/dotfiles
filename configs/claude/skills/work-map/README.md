# work-map — 実装の背景

手順と規則は [SKILL.md](SKILL.md) にある。ここには実装時の背景を残す。

## 制約の根拠

| 制約 | 根拠 |
| --- | --- |
| publish しない | 公開ページは元ファイルを消しても残る（自動削除は Team/Enterprise の管理機能）。破棄が既定という前提と衝突する |
| 外部リクエスト 0 | CDN 参照が1つでもあると、ファイルを渡した先やオフラインで壊れる |
| `<head>` から自分で書く | Artifact なら publish 時に外殻が被さるが、ローカルには無い。`charset` 宣言を欠くと `file://` で日本語が化ける |
| mermaid を使わない | claude.ai の viewer 側の機能で、ファイルで渡した先では素のテキストになる |
| フォントを埋め込まない | 日本語は CJK カバレッジが要り最低でも数百 KB。更新のたび全体を再出力する使い方では、これが最大の恒常的コストになる |
| 書き先は `~/Claude/scratch/` | リポジトリに書くと commit 事故になる。パスが短く辿れ、セッションを跨いでも残る |

フォントの1点は、組み込み design skill が指示する「`@font-face` を data URI で埋め込む」を**意図的に外している**。ラテン専用フォントを前提にした指示で、日本語では成立しない。

**社内限定の共有はファイル経路でしか成立しない。** 組織内スコープの共有は Team/Enterprise の機能で、Pro/Max では公開リンクしか選べない。

## 見た目を assets/ に置く理由

組み込みの design skill は artifact 構築時に効き、プロジェクトのデザインシステムを探す（優先順位は プロンプト > プロジェクト > Claude 自身の選択）。**この skill は publish しないので、その経路は当てにできない。**

そのため見た目の定義は `assets/head.html` だけに置いた。SKILL.md に CSS を散文で書くと、生成のたびにモデルが再構成してブレる。

**shadcn/ui は使えない。** Tailwind CSS が必須でコンポーネントは `.tsx`。ビルド工程を前提とする以上、単一ファイル自己完結とは両立しない。転用したのは視覚語彙だけ — CSS カスタムプロパティによるトークン命名、角丸スケール、中間色の階調。

## 図の選定

### 有向グラフ — dagre を同梱する

外部リクエスト 0 は CDN を禁じるだけで、**ライブラリをインラインに埋め込めば満たせる**。`@dagrejs/dagre` 3.0.0 は 39 KB、依存は `@dagrejs/graphlib` のみ。

**トークンは消費しない。** `assets/build.sh` がファイルを結合するので、97,200 バイトのコードが会話を通ることはない。組み立てを散文の手順でなくスクリプトにしたのは、次のセッションが同じ手順を再導出してライブラリをインラインに出力する事故を防ぐため。

**ライセンス。** dagre・graphlib とも MIT（Chris Pettitt, 2012-2014）。再配布の条件は著作権表示とライセンス全文を複製物に含めること。v3 は minify でライセンス表示が落ちているので生成物の冒頭に付ける。**v1 系は BSD-3-Clause の文言も抱えているため使わない。**

mermaid も同じ方法で埋め込めるが採らない。3.5 MB と 90 倍近い上に、描画までライブラリが行うのでノード幅が不揃いになり状態の色分けが消える。状態を見分けさせたいので、見た目の制御を手放す取引が割に合わない。

### チャート — ライブラリを使わない

46 点の時系列を、スケール変換・目盛りの丸め・ラベルの間引き・パス生成まで含めて **74 行**で描けた。

グラフのレイアウトは交差を減らす最適化問題で自前は非現実的だが、チャートの座標変換は値域をピクセル域へ写す線形写像で書ける。dagre を入れた必然性はチャートには無い。

**`d3-scale`（15 KB・ISC）を足す判断点は、目盛り生成が込み入る要求が出たとき** — 対数軸、時間軸の自動目盛り、積み上げなど。自前の代償は境界のバグで、目盛り上限が最大値を超えないとピークが枠外に出る。`d3-scale` の `nice()` が正しく扱う部分にあたる。

描画まで行う uPlot と Chart.js は canvas に描くので、SVG で組んだ見た目と揃わず採らない。

### 集合の重なり — 表を既定にする

3集合で比べると、速さは問いによって割れる。要素や属性を1つ指して引く問い（「レビューはどの図を使う？」）は表が速く、重なりや存在しない組み合わせを問う問い（「両方使うのは？」）はベン図が速い。

それでも表を既定にしたのは次の2点による。

- **ベン図が勝つ問いは一度分かれば済む。** 「状態表を使わない場面は無い」と分かればその図の役目は終わる。作業中に繰り返し引くのは要素起点の問いのほう
- **要素が増えるとベン図だけが壊れる。** 表は行が伸びるだけだが、ベン図は1領域2件で改行が要り、3〜4件で破綻する

3集合が上限なのは、4集合には 16 通りの領域が要るのに円 4 つでは 14 通りしか作れないため。対角どうしだけが重なる領域が物理的に存在しない。

## なぜ出所を持たせるか

出所を辿れれば情報の価値を評価できる。「この主張はどれくらい信じてよいか」を読むたびに思い出さずに済むので、認知負荷を下げるという目的に直接効く。

**一次情報が無い場合を明示するのが肝。** リンクが無いものが「まだ調べていない」のか「自分の判断」なのか「根拠の弱い推測」なのか区別できなければ、価値の評価はできない。

## 色と行長の判断基準

実値は `assets/head.html` にある。値を変えるときの基準は次の通り。

- **地は純グレーを避け、アクセント側へわずかに寄せる。**
- **本文の文字は地との差をしっかり取り、階調は見出しとラベルの側で作る。** 本文を薄い灰色に置くと見出しとの差が開きすぎて弱く見える
- **状態色はアクセントとは別系統に予約し、系列色として使い回さない。** 該当する実データが無い状態は語彙ごと持たない
- **単一テーマ（ライト固定）。** 作業中に読むだけのページに2組のトークンは要らず、定義が減るぶん再出力も軽くなる
- **コントラストは計算する。** 0.7rem のラベルで 4.5:1 を割っていても、スクリーンショットでは気づけない
- **行長の制限は本文にだけ掛ける。** 図・表・タイムラインは画面の広さをそのまま使う。ページ全体を1つの狭いカラムに収めると、ワイドディスプレイで画面の3分の1しか使わない

## 未確定の論点

1. **同梱ライブラリの更新** — dagre をバージョン固定で抱えるので、不具合や脆弱性が出ても自動では上がらない。更新の契機を決めていない
2. **図の型を5種で打ち止めにするか** — 5つのユースケースはいずれも既存の型で説明できたが、実際に使ってみるまで足りるかは分からない
