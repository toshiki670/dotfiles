# work-map — 実装の背景

手順と規則は [SKILL.md](SKILL.md) にある。ここには実装時の背景を残す。

## 制約の根拠

| 制約 | 根拠 |
| --- | --- |
| publish しない | 公開ページは元ファイルを消しても残る（自動削除は Team/Enterprise の管理機能）。破棄が既定という前提と衝突する |
| 外部リクエスト 0 | CDN 参照が1つでもあると、ファイルを渡した先やオフラインで壊れる |
| `<head>` から自分で書く | Artifact なら publish 時に外殻が被さるが、ローカルには無い。`charset` 宣言を欠くと `file://` で日本語が化ける |
| フォントを埋め込まない | 日本語は CJK カバレッジが要り最低でも数百 KB。更新のたび全体を再出力する使い方では、これが最大の恒常的コストになる |
| 書き先は `~/Claude/scratch/<案件>/` | リポジトリに書くと commit 事故になる。案件でディレクトリを切ると、終わったときにまとめて捨てられる。日付を付けないのは、日をまたぐ検討で同じ案件が分裂するため |

フォントの1点は、組み込み design skill が指示する「`@font-face` を data URI で埋め込む」を**意図的に外している**。ラテン専用フォントを前提にした指示で、日本語では成立しない。

**社内限定の共有はファイル経路でしか成立しない。** 組織内スコープの共有は Team/Enterprise の機能で、Pro/Max では公開リンクしか選べない。

## 見た目を assets/ に置く理由

組み込みの design skill は artifact 構築時に効き、プロジェクトのデザインシステムを探す（優先順位は プロンプト > プロジェクト > Claude 自身の選択）。**この skill は publish しないので、その経路は当てにできない。**

そのため見た目の定義は `assets/head.html` だけに置いた。SKILL.md に CSS を散文で書くと、生成のたびにモデルが再構成してブレる。

**shadcn/ui は使えない。** Tailwind CSS が必須でコンポーネントは `.tsx`。ビルド工程を前提とする以上、単一ファイル自己完結とは両立しない。転用したのは視覚語彙だけ — CSS カスタムプロパティによるトークン命名、角丸スケール、中間色の階調。

## 図の選定

### mermaid を同梱する

外部リクエスト 0 は CDN を禁じるだけで、**ライブラリをインラインに埋め込めば満たせる**。mermaid 11.16.1 の `mermaid.min.js` は 3,566,058 バイト、成果物は約 3.5 MB になる。

**トークンは消費しない。** `assets/build.sh` がファイルを結合するので、そのコードが会話を通ることはない。組み立てを散文の手順でなくスクリプトにしたのは、次のセッションが同じ手順を再導出してライブラリをインラインに出力する事故を防ぐため。

**build 時に描かせて SVG だけを埋める案は採らない。** 出力は 54 KB で済むが、部分編集が効かなくなる。状態の遷移や行の追加は確認を取らず高頻度に反映すると決めており、いまはノードの状態を1語書き換えれば次に開いた瞬間に反映される。プリレンダだと同じ更新が組み直しになる。同梱で失う「開くまで構文エラーに気づけない」性質は build 検査で埋める。

**ライセンス。** mermaid 本体は MIT（Knut Sveidqvist, 2014-2022）で、著作権表示とライセンス全文を複製物に含めることが条件。バンドルは埋め込んだ依存（dompurify・js-yaml・lodash-es・cytoscape）の表示を "Bundled license information" として自ら抱えているので、無改変で置けばそのぶんは満たされる。dompurify だけ Apache-2.0 と MPL-2.0 の選択制で、**MPL-2.0 を選ぶ** — Apache-2.0 はライセンス全文の同梱を求めるが、MPL-2.0 が求めるソース入手経路の告知はバンドル内表示の upstream URL が果たす。

**色はページのトークンから渡す。** `head.html` の `--mm-*` を `render-mermaid.js` が読んで `themeVariables` にする。断片へ `classDef` で色を書くと、断片は生成のたび書き直されるので値がずれる。状態の3語（`settled` / `open` / `warn`）だけは CSS 側で当てていて、そこには `!important` が要る。mermaid が注入する規則は `#mermaid-<id> .node rect` と ID 付きで、クラスセレクタでは特異性が届かない。

**囲みと出所リンクは mermaid の出力に乗せる。** `class <subgraph の id> <語>` は `g.cluster` に届く。`click` は `securityLevel` が既定（strict）のままでも `xlink:href` を出す。囲みは縁だけで分ける — 塗ると中のノードの塗りと競り、同じ語のノードを置いた瞬間に境目が消える。リンクは本文と同じ色では示せない。字の色は mermaid が `.nodeLabel` へ直接当てるので `a` の色が届かず、下線にする。

型の許可リストは作らない。既存の部品が勝つと実測できた役だけを塞ぎ、それ以外は自由に使う（塞ぐ役・代わりに使う部品・落ちるものは [SKILL.md](SKILL.md) の表にある）。build が弾いたときに名指しする部品もそこから来る。**理由の散文を `build.sh` へ書き写さない** — 型を1つ増減するたび両方を直すことになる。テーマ変数は型ごとに別系統なので、写像はその型を実際に使うときに足す。

**塞ぎは検査の上に、代わりの部品の名前を足す。** 検査が出せるのは症状だけで、代わりに何を使えばよいかは言えない。表にある落ちものには、そもそも検査に掛からないものと、落ちたものを削れば検査を通ってしまうものの両方がある。

### チャート — mermaid に任せる

量の時系列は `xychart-beta` で描く。面の塗りと最大値の注記は出ない。

抜けた日をどう扱うかは書き手が決める。0 を書けば谷になり、省けば横軸が「観測のあった日」に変わる。どちらを選ぶかは図で言いたいことによるので、機械が一律に決められない。

### 集合の重なり — 表を既定にする

3集合で比べると、速さは問いによって割れる。要素や属性を1つ指して引く問い（「レビューはどの図を使う？」）は表が速く、重なりや存在しない組み合わせを問う問い（「両方使うのは？」）はベン図が速い。

それでも表を既定にしたのは次の2点による。

- **ベン図が勝つ問いは一度分かれば済む。** 「状態表を使わない場面は無い」と分かればその図の役目は終わる。作業中に繰り返し引くのは要素起点の問いのほう
- **要素が増えるとベン図だけが壊れる。** 表は行が伸びるだけだが、ベン図は1領域2件で改行が要り、3〜4件で破綻する

描くのは `venn-beta` に任せる。円の配置もラベルの位置も向こうが決める。描かれるのは `union` を書いた組み合わせで、書かなければその2つは重ならない — 完全なベン図ではなく Euler 図が出る。そのぶん4集合でも図としては成立するが、3集合を上限にするのは、領域が増えるほど1領域の面積が縮んで改行の限界が早く来るため。

**3つ以上を束ねた `union` は、内側の交差を自分で作る。** 3集合で `union A, B, C` だけを書くとラベルは `A` `B` `C` と束ねたぶんの4つに見えて、実際には A∩B・B∩C・A∩C が空ラベルの領域として増える（テキスト要素は7個になる）。高階の `union` を書いたら下位の領域にも記号を与える。

set 名に日本語は使えず（Lexical error になる）、ASCII の識別子にラベルを `["…"]` で与える。面積の重みは `set A["A"]:20` のようにコロンで続ける（空白区切りは通らない）。領域へ文を足す `text A1["x"]` と、色を直接書く `style A fill:red` も通るので、**`style` は `classDef` と同じ扱いで断片に書かない** — 色の出所を1箇所に保つ。

## build 時に描いて確かめる

`assets/check.js` を一時複製にだけ足し、headless Chrome で描かせて結果を `document.title` へ書き出す。生成物側には残らない。判定は広い幅（1440）と、レールが畳まれる狭い幅（480 を渡すと実効 500）の2回。

**Chrome は `--user-data-dir` を渡すと DOM を吐いたあと終了しない。** 使い捨てプロファイルの初回起動の後始末が残り、90 秒待っても返らない（プロファイルを渡さなければ 2.5 秒で終わる）。かといってプロファイル無しでは利用者の実プロファイルを触る。そこでバックグラウンドで起こし、`WMCHECK.*</title>` が出たところで止める。閉じタグまで出ていれば JSON は途中で切れていない。

**ラベルのはみ出しは、テキストノードを Range で選んで測る。** 字を切るのは `foreignObject` なので比較相手もそれにする。**要素の矩形は使えない** — 中の `div` も `span` も `p` も `foreignObject` にクランプされ、`getBoundingClientRect()` がその箱と同じ値を返すので、定義上ずれようがない。`selectNodeContents(要素)` も同じ値になるため、`setStart` / `setEnd` でテキストノードそのものを選ぶ。`div.scrollWidth` は溢れていても `clientWidth` と一致するので、これも使えない。

陽性対照は、mermaid が測り終えたあとに `letter-spacing` を注入して字だけを広げる形で取る（箱の側を縮める対照では、比較の算術は試せても字の測り方が試せない）。この対照で 34.9 px を検出する。

**ラベルどうしの重なりは別に見る。** はみ出しの検査は `foreignObject` か、図形を持つ `g.node` を比較相手にするので、`<text>` だけで組む型は両方に掛からない。venn がそれで、3集合に長い日本語ラベルを置くと隣の字に乗ったまま素通りしていた。同じ SVG 内の `<text>` を総当たりで見て、矩形が縦横とも 0.5 px を超えて重なったら落とす。誤発火は flowchart / sequence / class / er / gitGraph / pie / architecture-beta で 0 件 — flowchart・class・er はラベルが `foreignObject` に入るので `<text>` を持たず、守備範囲が重ならない。

**`themeVariables` にフォントを渡すとラベルが欠けるという報告は、この構成では再現しなかった。** `--mm-fontFamily` でも `%%{init}%%` でも超過は 0 のままで、`htmlLabels` を切って `<text>` にしても余白は 11 px 残る。mermaid がページの CSS を適用した DOM 上で測るので、箱がテキストに追従するのだと見ている。それでも渡さないのは、日本語は system のフォールバックで足りて渡す利得が無いため。

なお `%%{init}%%` の値に引用符が入っていると、その指定は黙って無視される（`{'fontFamily': 'Hiragino Sans'}` は効き、`{'fontFamily': '"Hiragino Sans", sans-serif'}` は効かない）。フォント指定の再現を試みるときはここで空振りしやすい。

**系列は色の差で見る。色数は数えない。** 印を並び順に1つずつ拾い、隣り合う組の ΔE と明るさの差、同じ色の重複、そして下地との差を測る。色の一覧に載っているかは問わないので、ページ側で色を足しても基準を割れば止まる。用意した色を使い切ると同じ色が回ってきて、重複で捕まる。

CIEDE2000 を検査へ持ち込んでいるのは、明るさの比だけでは色相の違いが 1.0 と出るため。拾う先は型ごとの印なので、系列を持つ型を新しく使うときは写像と一緒にここも足す。

**届いているかは build へ寄せない。** 語が境界の内か外かは読み手で決まるので、語形からは判定できない。実装の語彙を並べた禁止一覧にすると、読み手がそのファイルを開きに行く場面で誤って弾く。

## なぜ出所を持たせるか

出所を辿れれば情報の価値を評価できる。「この主張はどれくらい信じてよいか」を読むたびに思い出さずに済むので、認知負荷を下げるという目的に直接効く。

**一次情報が無い場合を明示するのが肝。** リンクが無いものが「まだ調べていない」のか「自分の判断」なのか「根拠の弱い推測」なのか区別できなければ、価値の評価はできない。

## 色と行長の判断基準

実値は `assets/head.html` にある。値を変えるときの基準は次の通り。

- **地は純グレーを避け、アクセント側へわずかに寄せる。**
- **本文の文字は地との差をしっかり取り、階調は見出しとラベルの側で作る。** 本文を薄い灰色に置くと見出しとの差が開きすぎて弱く見える
- **状態色はアクセントとは別系統に予約し、系列色として使い回さない。** 該当する実データが無い状態は語彙ごと持たない
- **系列色は隣り合う組で見る。上限を色数で決めない。** 並び順で隣り合う2色が ΔE 18.5・明るさの差 2.13 倍を満たすかどうかがすべてで、満たす限り増やせる。実測で見分けが付いた中の下限を採った。色相だけで分けると色覚によっては潰れるので明るさも要る — 状態を形でも分けているのと同じ筋
- **明暗を交互に置き、色相を割り振ると8色まで並ぶ。** 同じ明るさの帯どうしは色相で分かれる。色相を一周させるぶん状態色の近くも通り、いちばん近い組で ΔE 17.5。使い回してはいないが、どちらかを動かすときはこの差を見る
- **印が下地の上に直接置かれる型（線・レーダー）は、下地との差も同じ基準で見る。** 円グラフは区画どうしが接していて境目の線が残るので、下地との差は問われない
- **塗りの上に字を載せる型があるので、各色は載る字の色を連れている。** 字を1色に固定すると置ける色が減る。暗い帯には地の色、明るい帯にはインクを当てて、どちらも 4.5:1 を超える
- **単一テーマ（ライト固定）。** 作業中に読むだけのページに2組のトークンは要らず、定義が減るぶん再出力も軽くなる
- **コントラストは計算する。** 0.7rem のラベルで 4.5:1 を割っていても、スクリーンショットでは気づけない
- **図の状態は色相を落としても分かれるようにする。** `open` は破線、`warn` は太い実線で分かれるが、`settled` と無印を分けているのは縁の明度差だけ（ノードで 3.29、囲みで 4.31）。縁の色を動かすときはこの差を保つ
- **行長の制限は本文にだけ掛ける。** 図・表・タイムラインは画面の広さをそのまま使う。ページ全体を1つの狭いカラムに収めると、ワイドディスプレイで画面の3分の1しか使わない

## 未確定の論点

1. **同梱ライブラリの更新** — mermaid をバージョン固定で抱えるので、不具合や脆弱性が出ても自動では上がらない。更新の契機を決めていない
2. **3.57 MB がリポジトリに載る** — ディスク観点では許容と判断したが、更新を重ねたときの履歴の太り方は見ていない
3. **build が Chrome に依存する** — 見つからなければ失敗する。検査を飛ばせる逃げ道は置いていない
