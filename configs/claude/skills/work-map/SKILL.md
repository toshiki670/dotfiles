# work-map — 作業中の理解を一枚に起こす

進行中の仕事について、経緯・状況・依存関係を単一の HTML ページへ起こす。読まれるのは**作業中に認知負荷が高くなったとき、あるいは理解が及んでいないと感じたとき**で、作業の再開時でも他人への説明用でもない。

したがってページの仕事は記録ではなく、**頭に収まらなくなったものを外に出して見えるようにする**こと。

## 方針（厳守）

- **読み手を決めてから書く。** 誰が読むかで、圧縮したまま置いてよい語と、解除して書くべき語が変わる。特定と境界の引き方は手順1。
- **情報は増やすのでなく構造化して減らす。** 網羅は目的ではない。いま負荷の原因になっているものだけを構造に落とす。関係する事実を全部書くと、外に出した先でもう一度同じ量に埋もれる。
- **先頭に来るのは未解決のもの。** 読み手はその仕事の経緯を追ってきていて、見失っているのは何が未解決かのほう。だから既知から未知へではなく、**未解決から既解決へ**並べる。状態を持つ表も同じで、未解決の行を上に置く。
- **主張には出所を持たせる。** 一次情報があるならリンクにする。無い場合は何に基づくかを語で示す（下記）。
- **単一ファイル自己完結。** 外部への通信を一切行わない。CSS と JS はインライン、画像は data URI。CDN 参照が1つでもあると、ファイルを渡した先やオフラインで壊れる。
- **既定は破棄。** `~/Claude/scratch/<案件>/` に置き、用が済んだら案件ごとディレクトリで捨てる。残すよう明示されない限り、リポジトリには書かない（commit 事故になる）。
- **自分の判断で作り始めない。** 起動されたときだけ作る。

## 手順

### 1. 読み手を決め、その人の負荷を掴む

**読み手はこのページを開く人間で、調べている自分ではない。** いま会話している相手か、その仕事を進めている当人。どちらか決まらないときは尋ねる。

**知識の境界は振る舞いと実装のあいだに引く。** 何がどう動くかは追っていても、それがどう書かれているかまでは読んでいない、というのが常態。作った本人でも同じで、前提の説明が要らないのは振る舞いについてだけ。ただし読み手がそのファイルを開きに行く場面（既存システムの把握）では、ファイル名や設定の名前は内側に入る。内か外かは語の見た目でなく、**読み手がそこへ手を伸ばすか**で決まる。

境界の外にある事実は、そのまま置かずに**言い換えるか、図に展開する**。1つの結論に落ちるなら言い換え、言い換えると条件が落ちるなら図にする（「2種類までしか塗り分けられない」は、3種類目を指定した図を並べれば見える）。

そのうえで、読み手がいま何を追えなくなっているのかを、会話の文脈から拾うか、短く尋ねる。**主題ではなく負荷の原因**を特定する。場面ごとに原因は決まっている:

| 場面 | 負荷の原因 | 主役の形 | 添える形 |
| --- | --- | --- | --- |
| 障害・不具合の調査 | 仮説が複数あり、どれを潰したか追えない | 仮説の状態表（生存 / 否定 / 未検証 と根拠） | 試したことの時系列 |
| 大きい実装の進行管理 | フェーズが多く、何で止まっているか見えない | 進捗の状態表 | ブロック関係の有向グラフ、残数 |
| 既存システムの把握 | 依存とデータフローが頭に入らない | 有向グラフ | 構成要素の表 |
| 設計の検討・意思決定 | 制約と帰結が連鎖し、選択肢が絡む | 有向グラフ（前提 → 帰結） | 論点表、決定の時系列 |
| 他人の成果物のレビュー | 指摘が散在し、重要度と対応状況が混ざる | 指摘の状態表 | 該当箇所の一覧 |

負荷の正体はたいてい「**複数のものが、それぞれ違う状態にあって、頭の中で追いきれない**」ことなので、どの場面でも状態表が中心に来る。

### 2. 形を選ぶ

上の表から引けないときは、**読み手がそこから何を取り出すか**で選ぶ:

| 取り出すもの | 形 |
| --- | --- |
| 順序 — いつ何が起きたか | 線形タイムライン |
| 全体の現在値 | 数値の一覧（レールに縦積み） |
| 個々の状態 | 状態表 + チップ |
| 関係・依存 | 有向グラフ |
| 量 — 並べただけでは形が見えないとき | チャート |

**チャートは点数が多いときだけ。** 2 個なら文中に書き、3〜5 個の比較は表で足りる。時系列と分布だけがチャートに値する。

量は `xychart-beta` で描く。日付を軸に置くときは幅とラベルの角度を渡す。46 点で測ると、どちらか一方でも落とすと隣の日付と重なって build が止まる。

```html
<div class="scroller"><pre class="mermaid">
%%{init: {'xyChart': {'width': 1100, 'xAxis': {'labelRotation': 45, 'labelFontSize': 10}}}}%%
xychart-beta
  title "エラー数"
  x-axis ["06-01", "06-02", …]
  y-axis 0 --> 25
  line [3, 5, …]
</pre></div>
```

**点数が増えたら幅も広げる。** 46〜60 点なら 1100、90 点なら 2000 が通った。足りなければ重なりで build が止まるので、そこで広げる。

**y 軸に題を付けない。** 目盛りの数字と重なり、`titlePadding` を広げても消えない。量の名前は図の題に書く。

**同じラベルを2度書かない。** x 軸は文字列でカテゴリを作るので、同じ字を並べると1つに畳まれ、線が同じ位置へ戻って形をなさない。日付をまたぐなら年月まで入れる。

**抜けた日をどう書くかは決める。** 0 を書けば谷として出て、省けば横軸が「観測のあった日」に変わり、間隔が日数を表さなくなる。どちらも図の主張が変わるので、言いたいことに合わせて選ぶ。なお「観測が無かった」こと自体は、どちらの書き方でも図には出ない（`line` は数値しか受けない）。

**何がどの分類に属するかは表で書く。** ベン図は「表では分かりにくい」と言われたときだけ、3集合を上限に `venn-beta` で描く。重なりは `union` を書いた組み合わせが描かれ、書き落とせばその2つは重ならない。ただし `union A, B, C` のように3つ以上を束ねると、内側の2集合の交差はラベルの無い領域として自動で生まれる（3集合なら3つ）。**その領域にも記号を与える。** 空のまま残すと、読み手には該当なしと区別できない。

**領域には記号だけを置き、中身は凡例へ回す。** 領域の面積は集合が増えるほど縮み、長いラベルは隣の字に乗る。build はこの重なりで落ちる。**集合と重なりは別の群にして、それぞれ縦に列挙する。** 記号が列で揃い、どちらの群の記号かを読み手が推測しなくて済む。

```html
<div class="figure">
  <div class="scroller"><pre class="mermaid">
venn-beta
  set A ["A"]
  set B ["B"]
  union A, B ["1"]
</pre></div>
  <div class="legends">
    <div class="legend stack">
      <b>集合</b>
      <span>A 障害・不具合の調査</span>
      <span>B 設計の検討</span>
    </div>
    <div class="legend stack">
      <b>重なり</b>
      <span>1 決定の時系列</span>
    </div>
  </div>
</div>
```

図は mermaid で描く。型の許可リストは作らない — flowchart 以外に要るものがあれば使ってよい。ただし次の役目は既存の部品が勝つと実測できているので渡さない。build が弾く。

| 役目 | 使うもの | 渡さない型 | 落ちるもの |
| --- | --- | --- | --- |
| 個々の状態 | 状態表＋チップ | `kanban` | 出所のリンク。`click` は解釈されず文字として描かれる |
| 順序（経緯） | `.track` | `timeline` | 理由の1文。入れると隣の列と重なる |

日本語がそのまま通らない型がある。

| 型 | 日本語 |
| --- | --- |
| flowchart / sequence / class / er | そのまま通る |
| `architecture-beta` | ラベルを引用符で囲む（`["通知基盤"]`）。囲まないと Lexer error |
| `gitGraph` | ブランチ名を引用符で囲む（`branch "開発"`）。`checkout` / `merge` の参照側も同じ。`id:` / `tag:` はそのまま通る |
| `sankey-beta` | ノード名に日本語が使えない。使うなら ASCII |
| `venn-beta` | set 名に日本語が使えない。ラベル（`["…"]`）は通る |

色は `assets/head.html` の `--mm-*` が握っている。いま写像があるのは flowchart のぶんだけで、別の型を使うときはその型の変数を足す。

### 3. ページを組み立てる

`assets/build.sh` で組み立てる。**ライブラリ本体はこのスクリプトが結合するので、コンテキストを通らない。** 配置されたファイルに実行ビットは付かないので `bash` 経由で呼ぶ。

```bash
bash ~/.claude/skills/work-map/assets/build.sh \
  -o ~/Claude/scratch/<案件>/<題名>.html \
  -c <本文の断片> -t "<タイトル>"
```

**書き先は案件ごとのディレクトリ。** 案件名は短いスラッグにし、**日付は付けない**（日をまたぐ検討で同じ案件が別ディレクトリへ分裂する）。同じ案件なら同じディレクトリを使い続ける。ディレクトリが無ければ build が作る。

図は本文の断片に直接書く。`<pre class="mermaid">` があれば build がライブラリを埋める。

```html
<div class="scroller"><pre class="mermaid">
flowchart LR
  s0["S0 事前調査"] --> s1["S1 スキーマ定義"]
  s1 -->|"再送の仕様待ち"| s2["S2 リトライ制御"]
  class s0,s1 settled
  class s2 open
</pre></div>
```

書くのは本文の断片だけで、CSS・骨格・ライブラリには触らない。骨格は次の順に並べる:

1. レール（左に固定） — 状態カウント・セクション目次・更新日
2. `.masthead` — 見出しと1段落の要約
3. `.next` — 次の一手を1つだけ
4. 負荷の原因を解く主役の形
5. 経緯（そこへ至った理由。**調査と決定だけを残し、試して捨てた道は書かない**）
6. 論点表

**同じ数値を2箇所に置かない。** レールにカウントを出したら本文側に再掲しない（更新のたび両方を直す羽目になる）。

### 4. 検証する

build が headless Chrome で描いてから確かめるので、通ったなら次は見なくてよい。落ちたときは書き出さずに理由を出す。

- mermaid が SVG を返したか（構文エラーはここで止まる）
- ラベルがノードの図形からはみ出していないか
- ラベルどうしが重なっていないか
- 文書幅が viewport を超えないか。広いときとレールが畳まれる狭いときの両方で見る
- 外部へ取りに行っていないか。実際の通信を見るので、書き方を変えてもすり抜けない
- 渡さない型を使っていないか

残るのは build が見ないもの。

- **レールのカウントと表の行数が一致するか。** 状態を1つ動かしたら両方を直す。
- **文字色を変えたらコントラスト比を計算する。** ラベル類は 0.7rem（約 11px）と小さく、WCAG の 4.5:1 が要る。スクリーンショットでは判定できない。
- **チャートの目盛り上限が最大値以上か。** 複数の値域で検算する。上限が max を超えないと最大点が枠外に出る。
- **初めて使う型は開いて見る。** 要素の重なりやラベルが隣の領域へ食い込む類は、その型の写像を書くまで build には見えない。

**最後に、届いているかを見る。** ここまでの検査はどれも、読み手に通じない語が並んだページを通す。境界の外にあるものは2通りの出方をするので、探し方を分ける。

**語 — ページに出てくる固有名詞と記号を書き出す。** ファイル名・設定名・識別子・型名・略語。形で見分けが付く。

**文 — 仕組みで説明した箇所を拾う。** 識別子を伴わないので形では見つからない。文を1つずつ読み、**読み手に見えている振る舞いを書いているのか、中でどう動くかを書いているのか**を答える。後者が該当する（「順に当てて最初に合ったものを使う」「上書きの経路が無い」のような書き方）。

どちらも**読み手がそこへ手を伸ばすか**を答え、No が付いたものが境界の外に残っている。手順1へ戻る。

**読み返しでは代えられない。** 書いた側には全部意味が通っていて、通ることと届くことの区別が付かない。

### 5. 更新する

**起動したあとは、なるべく最新に保つ。** 一度作って放置しない。作業が進むたびに反映するが、変更の大きさで扱いを分ける:

| 変更 | 扱い |
| --- | --- |
| 状態の遷移、行の追加、数値の更新、経緯への1件追加 | 確認を取らず、その場で高頻度に反映する（部分編集） |
| ブロックの追加・削除、構造の変更、全体の書き直し | 要件を固めて確認を取ってから（再ビルド） |

境界は**部分編集で済むか、全体を組み直すか**。組み直しはページ全体のトークンを毎回払うので、そこに確認の関門を置く。

## 出所の語彙

状態（解決したか）とは**別の列**に置く。混ぜると「確定しているが推測に基づく」という最も危ない組み合わせが表現できなくなる。

| 出所 | 意味 |
| --- | --- |
| リンク | 一次情報がある。Slack のメッセージ、設計書、PR の該当箇所、main 上の実装位置、チケット |
| 実測 | 自分で計測・実行して確かめた |
| 合意 | 関係者と決めた。会話が出所でリンク先は無い |
| 推測 | 根拠が弱く、裏取りが要る |
| — | まだ何も無い |

- ラベルは短くする（`PR #123`、`設計書`、`SRE-4821`）。URL をそのまま貼ると負荷を上げる側に働く
- コード位置は**コミット SHA を固定した permalink** にする。ブランチ相対のリンクは行がずれて別の場所を指すようになる
- **テキストリンクに限る。** favicon やプレビュー画像を出した時点で外部通信が発生し、自己完結が壊れる
- **図のノードからも張れる。** `click <id> "<URL>"` と書くと、その字に下線が付く

## 状態の語彙

記号・語・色の3つで示し、色だけに載せない。該当する実データが無い語は使わない。

| 状態 | チップ |
| --- | --- |
| 確定 | `chip settled`（✓） |
| 未確定 | `chip open`（?） |
| 要注意 | `chip warn`（⚠） |

有向グラフも同じ語彙を使う。`settled` が確定した前提、無印が導かれる帰結、`open` が未確定、`warn` が要注意。囲み（subgraph）は id を書けば同じ語を取る。4つは色相を落としても見分けが付く（線の形・太さ・縁の明度で分けてある）。mermaid には `class` 文で意味だけを書く。

```text
class s0,s1 settled
class s5 open
class s7 warn
class g1 settled
```

**断片に色を書かない。** `classDef` でも `style` でも同じ。色の出所はページのトークン1箇所に置いてあり、断片へ書き写すと次に組み直したときずれる。

## 渡す・残す

既定は破棄だが、そこから先の経路が2つある。どちらも `~/Claude/scratch/` の外へファイルをコピーするだけで、公開ページは介さない。

- **渡す** — 単一ファイル自己完結なので、添付でもコピーでもそのまま開ける
- **残す** — リポジトリに置くなら、その時点で寿命が変わるので commit 対象として扱う

Artifact として publish しない。公開したページは元ファイルを消しても残り、破棄が既定という前提と噛み合わない。
