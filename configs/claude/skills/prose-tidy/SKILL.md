# prose-tidy — 文書の無駄を削る

人間の読者に向けて書く **prose 文書**を、読者が実際に必要とする情報密度の観点でレビューし、事実の羅列ではなく必要最小限に絞る。内容の正しさ（事実関係）は見ない（correctness は別の役目）。

**重複・陳腐化・惰性で残ったものの判定は自分で行わず、`debt-audit` agent へ渡す**（手順4・7）。書いた本人が判定すると素通りするため。この skill が持つのは、読者との距離から決まる観点と、debt-audit へ渡す材料の集め方。

## 前提

- 対象はファイル種別で決めない。**人間が読み、正誤ではなく情報密度・構成が問題になる text か**で判断する。Markdown 文書(README / CONTRIBUTING / `docs/**/*.md` 等)・PR/Issue 本文・レビューコメント・commit message の body・CLI の help/エラーメッセージ・コード内平文コメント・`show-me` が作る HTML ページ等が該当しうる。
- 特定言語の doc コメント生成ツールが解釈する専用記法(例: Rust の `//!` / `///`)は、その記法特有の構造(自動生成される要素一覧・相互参照リンク等)をこの skill の一般則で判定すると誤判定しうる。手順1でその記法を扱う専用の skill・rule が見つかれば、その範囲はそちらに譲る。
- 自動生成される文書（CHANGELOG.md 等）は対象外。
- model 向けの設定文書(CLAUDE.md・skill 定義・memory ファイル等、人間読者を前提としない文書)には観点2(用語は使う前に定義する)・観点3(抽象語彙を持ち込まない)は当てはまらない。
- 判定はパターンの機械的な一致ではなく、**都度その一文を読んで**「読者はこの一文から何を得るか」を考えて行う。同じ字面でも文脈次第で残す/消すが変わる。

## チェック観点

### 1. 前置きが空語かどうかは文書の目的で決める

「本ドキュメントでは〜について説明する」のような前置きは、**読者が既に知っている・何も予告していないときだけ**空語になる。正式な仕様書・チュートリアルなど、要約的な前置きがジャンルの慣行として期待される文書では、同じ形の文が空語ではなく構造的なシグナルとして機能する。一律に禁止するのではなく、次の手順で判定する。

1. その前置きを消したら、読者は何を失うか(主題・この先で何が得られるかの予告)を考える。何も失わないなら空語。
2. そのジャンルで前置きが慣行として期待されているか(手順1の調査で確認)。期待されているなら残す。

### 2. 用語は使う前に定義する

ドメイン固有の語彙が、定義される前の文で使われていないか確認する。文書の冒頭・上位セクションから個別セクションへ、「既知から未知へ」語彙を積み上げる。まだ登場していない語をいきなり使わない。

### 3. この文書を書く際に使った内部の抽象語彙を持ち込まない

社内的な設計方針の議論で使う抽象語彙（例: SSOT・ライフサイクル・安定/揮発等）を、その語彙を前提としない読者向けの文書にそのまま書いていないか確認する。**これらの語自体は他の文脈でも一般的に使われうる**(SSOT は他プロジェクト独自の Source of Truth を指すこともあり、安定/揮発も他の設計原則が独自に定義しうる)。語が出現しているかどうかではなく、**その用法が実際に書き手側の内部設計方針を参照しているか**で判断する。参照しているなら具体的な技術的事実に置き換える。

## 手順

1. **実行環境を調査する。**
   - Claude Code の Auto Memory(`~/.claude/projects/<slug>/memory/`、`<slug>` は cwd の絶対パスの `/` を `-` に置換したもの)が使えるなら、まず `doc-conventions.md` の有無を確認する。あれば読んで規約・傾向として使い、以下の再調査はしない。
   - 無ければ、このプロジェクトに対象文書の種別・記法に関わる skill・rule・CONTRIBUTING 等の文書規約がないか確認する。明文化された規約が無くても、同じジャンルの既存ファイルを実際に読み、そこから読み取れる傾向(トーン・構成・記法)を把握する。見つけた内容は(Auto Memory が使えるなら)`doc-conventions.md` として保存し、次回以降はそちらを参照する。内容が現状と食い違うと気づいたら、その場で実態に合わせて更新する。
   - **見つかった規約・傾向は、観点1〜3のどれに対してもこの skill の一般則より優先して適用する**(例: 空語に見える前置きを意図的に使う文体規約、用語を定義せず使う前提のグロッサリ等)。対象文書の種別・記法に特化した skill が見つかれば、その範囲は重複して適用しない。
2. **スコープを決める（曖昧なら聞く）**: 対象ファイル1つか、指示された diff 全体か。依頼されていない範囲(プロジェクト全体等)へ自発的に広げない。
3. 対象文書を実際に読み、観点1〜3を当てる。
4. **debt-audit へ渡す材料を揃え、呼ぶ。** 判定はこの skill では行わない。渡す材料は次のとおり。
   - **対象文書と、この tidy を頼んだ文（そのまま）。**
   - **その文書が「この先も編集され続ける」のか「一度書いたら書き換えない記録」なのか。** 前者は書いた時点の事実がいずれ変わり、後者はその場で自己完結させる方が後から読む人には価値が高い。どちらに当たるかは手順1で見つけた規約による。
   - **出所の候補。** 同じ内容を既に持っている可能性のある場所を、実際に探して渡す。仕様書・リンク先ドキュメント・CI のエラーメッセージ・自動生成物・その記述を解釈する実装自身の構造化ドキュメント(言語標準の doc コメント生成規約。例: Rust の rustdoc、Python の docstring、Go の godoc)。**1つの変更が複数ファイルの説明文の並行編集を要求したなら、それ自体が出所を持つ兆候**なので、その全ファイルを渡す。同じ記述が複数の sibling ファイル(各 bin の `cli.rs` 等)にあるときは全 sibling を渡す — 慣習か直し忘れの横展開かは、揃えて見ないと分かれない。
   - **経緯に見える記述は、実装のメカニズム・時系列(How/History)なのか設計の理由(Why)なのかを見分けて添える。** どちらとして扱うかは debt-audit が決める。
5. 観点1〜3 と debt-audit の返答を突き合わせ、編集する。少数のファイルは直接編集する。10ファイルを超えるような機械的な一括修正は、判定基準と before/after を明記したうえでサブエージェントへ委任してよい。
6. **削除・移動した見出しやセクションへのリンク・アンカー参照が壊れていないか確認する。**
7. **自分の diff を debt-audit へ渡す。** 削る依頼で情報量が増えるのは繰り返し起きている失敗なので、仕上げの diff も手順4と同じ依頼文を添えて監査に掛ける。

## 出力

1. 削除した箇所の一覧（ファイル・削除理由を観点1〜3か debt-audit の分類で）。
2. 残すと判断した境界線上の箇所と、その理由（残す判断も明記して次回に活かす）。
3. リンク切れ確認の結果。
4. 手順7 で debt-audit が返したもの（該当なしならそう書く）。
