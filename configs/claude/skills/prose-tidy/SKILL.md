# prose-tidy — 文書の無駄を削る

読者が実際に必要とする情報密度の観点で text をレビューし、事実の羅列ではなく必要最小限に絞る。内容の正しさ（事実関係）は見ない（correctness は別の役目）。

**重複・陳腐化・惰性で残ったものの判定は自分で行わず、`debt-audit` agent へ渡す**（手順4・7）。この skill が持つのは、読者との距離から決まる観点と、debt-audit へ渡す材料の集め方。

## 前提

- 対象はファイル種別で決めない。**正誤ではなく情報密度・構成が問題になる text か**で判断する。読み手は人間とは限らず、skill 定義や CLAUDE.md のようにモデルが読む設定文書も対象になる。
- 自動生成される文書（CHANGELOG.md 等）は対象外。
- 判定はパターンの機械的な一致ではなく、**都度その一文を読んで**「読者はこの一文から何を得るか」を考えて行う。同じ字面でも文脈次第で残す/消すが変わる。

## チェック観点

### 1. given-new contract — 読み手が持っていない情報を既知として差し出さない

既知(Given)として差し出した情報に、読み手の記憶の中でただ1つの先行詞(Antecedent)が対応するか確認する。無ければ読み手は自分で組み立てるしかなく、別の先行詞を掴めばこちらの意図とは違うものを読む([Clark & Haviland 1977](https://web.stanford.edu/~clark/1970s/Clark,%20H.H.%20_%20Haviland,%20S.E.%20_Comprehension%20and%20the%20given-new%20contract_%201977.pdf) の maxim of antecedence)。先行詞は文書内の記述とは限らず、読み手が既に持っている知識でもよい。目安は、前提となる事実が示される前に前提として扱われていないか、ドメイン固有の語彙が定義される前に使われていないか、冒頭・上位セクションから個別セクションへ既知から未知へ積み上がっているか。

### 2. curse of knowledge — 書く側の前提を読み手も持っていると思い込まない

書き手だけが知っているものを、読み手も知っている前提で置いていないか確認する。固有名詞、記号、ファイル名、設定名、識別子、型名、略語はそれぞれについて、読み手が文書の目的を果たすためにその対象を参照・操作する必要があるかを答える。内部の仕組みを説明した文は、読み手に見える振る舞いを知れば足りないかを答える。必要がなければ、読み手に必要な具体的事実へ置き換える。ただし依頼が**用語を残す行き先**(押すと開く説明など)を示しているときは、用語だけは置き換えず、前提にできないと判定したものをそのまま返す。

社内的な設計方針の議論で使う抽象語彙（例: SSOT・ライフサイクル・安定/揮発等）も同じように見る。**これらの語自体は他の文脈でも一般的に使われうる**(SSOT は他プロジェクト独自の Source of Truth を指すこともあり、安定/揮発も他の設計原則が独自に定義しうる)。出現や形ではなく、**その用法が実際に書き手側だけが持つ知識を前提としているか**で判断する([Camerer, Loewenstein & Weber 1989](https://www.cmu.edu/dietrich/sds/docs/loewenstein/CurseknowledgeEconSet.pdf)、文章への適用は Pinker, *The Sense of Style* 2014)。

## 手順

1. **実行環境を調査する。**
   - Claude Code の Auto Memory(`~/.claude/projects/<slug>/memory/`、`<slug>` は cwd の絶対パスの `/` を `-` に置換したもの)が使えるなら、まず `doc-conventions.md` の有無を確認する。あれば読んで規約・傾向として使い、以下の再調査はしない。
   - 無ければ、このプロジェクトに対象文書の種別・記法に関わる skill・rule・CONTRIBUTING 等の文書規約がないか確認する。明文化された規約が無くても、同じジャンルの既存ファイルを実際に読み、そこから読み取れる傾向(トーン・構成・記法)を把握する。見つけた内容は(Auto Memory が使えるなら)`doc-conventions.md` として保存し、次回以降はそちらを参照する。内容が現状と食い違うと気づいたら、その場で実態に合わせて更新する。
   - **見つかった規約・傾向は、この skill の一般則にも debt-audit の返答にも優先する**(例: 用語を定義せず使う前提のグロッサリ、ジャンルの慣行として残すべき記述)。
2. **スコープを決める（曖昧なら聞く）**: 対象ファイル1つか、指示された diff 全体か。依頼されていない範囲(プロジェクト全体等)へ自発的に広げない。
3. 対象文書を実際に読み、観点1・2 を当てる。
4. **debt-audit へ渡す材料を揃え、呼ぶ。** 判定はこの skill では行わない。渡す材料は次のとおり。
   - **対象文書と、この tidy を頼んだ文（そのまま）。**
   - **その文書が「この先も編集され続ける」のか「一度書いたら書き換えない記録」なのか。** どちらに当たるかは手順1で見つけた規約による。
   - **出所の候補。** 同じ内容を既に持っている可能性のある場所を、実際に探して渡す。仕様書・リンク先ドキュメント・CI のエラーメッセージ・自動生成物・その記述を解釈する実装自身の構造化ドキュメント(言語標準の doc コメント生成規約。例: Rust の rustdoc、Python の docstring、Go の godoc)。**1つの変更が複数ファイルの説明文の並行編集を要求したなら、それ自体が出所を持つ兆候**なので、その全ファイルを渡す。同じ記述が複数の sibling ファイル(各 bin の `cli.rs` 等)にあるときは全 sibling を渡す — 慣習か直し忘れの横展開かは、揃えて見ないと分かれない。
   - **経緯に見える記述。** どう扱うかは debt-audit が決める。
5. 観点1・2 と debt-audit の返答を突き合わせ、編集する。少数のファイルは直接編集する。10ファイルを超えるような機械的な一括修正は、判定基準と before/after を明記したうえでサブエージェントへ委任してよい。
6. **削除・移動した見出しやセクションへのリンク・アンカー参照が壊れていないか確認する。**
7. **自分の diff を debt-audit へ渡す。** 手順4と同じ依頼文を添えて監査に掛ける。

## 出力

1. 削除した箇所の一覧（ファイル・削除理由を観点1・2 か debt-audit の分類で）。
2. 残すと判断した境界線上の箇所と、その理由（残す判断も明記して次回に活かす）。
3. リンク切れ確認の結果。
4. 手順7 で debt-audit が返したもの（該当なしならそう書く）。
