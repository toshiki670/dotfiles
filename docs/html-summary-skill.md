# 作業中の理解を HTML でまとめる Skill — 要件定義

## 目的

複雑な仕事の**経緯・状況・依存関係**を、作業している本人が「いまどこにいるか」を掴むために HTML へ起こす。その共通フォーマットとデザインを `work-map` skill として `configs/claude/skills/work-map/` で管理する。

## 非目的

- 保管される文書を作ること。既定は破棄で、残すのは明示指示があるときだけ
- 共有ページ（Artifact）として公開すること
- チャート描画一般。実データの量的比較は `dataviz` skill の担当

## 確定した制約

| 制約 | 根拠 |
| --- | --- |
| ローカルの単一 HTML ファイルのみ。publish しない | 公開ページは元ファイルを消しても残る（自動削除は Team/Enterprise の管理機能）。破棄が既定という要件と衝突する。加えて claude.ai へのアップロードが発生しない |
| 外部リクエスト 0。CSS/JS はインライン、画像は data URI | ファイルで渡す・オフラインで開くため。CDN 参照が1つでもあると渡した先で壊れる |
| 完全な HTML ドキュメントとして書く（`<!doctype>` / `<head>` / `<meta charset="utf-8">`） | Artifact なら publish 時に外殻が被さるが、ローカルには無い。charset 宣言を欠くと `file://` で日本語が化ける |
| mermaid を使わない | claude.ai の viewer 側の機能で、ファイルで渡した先では素のテキストになる |
| フォントは埋め込まずシステムスタック | 日本語ページなので CJK カバレッジが要り、最低でも数百 KB。更新のたび全体を再出力する使い方では、これが最大の恒常的トークンコストになる |
| 書き先は `~/Claude/scratch/<題名>.html` | リポジトリに書くと commit 事故になる。ディレクトリ名が使い捨てを語るので、中のものは消してよいと一目で分かる。パスが短く自分で辿れ、セッションを跨いでも残る。破棄は `trash` で明示的に行う |

フォントの1点は、Claude の組み込み design skill が指示する「`@font-face` を data URI で埋め込む」を**意図的に外している**。ラテン専用フォントを前提にした指示で、日本語では成立しない。

## 渡す・残す

既定では `~/Claude/scratch/` に置いて用が済んだら捨てるが、そこから先の経路が2つある。どちらも**ファイルをそのディレクトリの外へコピーする**という同じ操作で、公開ページを介さない。

- **渡す** — 同僚に見せる。単一ファイル自己完結なので、添付でもコピーでもそのまま開ける。組織内スコープの共有は Team/Enterprise プランの機能で、Pro/Max では公開リンクしか選べないため、社内限定はこのファイル経路でしか成立しない
- **残す** — 破棄せず取っておく。リポジトリに置くなら、その時点で寿命が変わるので commit 対象として扱う

## Claude の推奨方針（調査結果）

- 組み込みの design skill が artifact 構築時に自動で効き、**まずプロジェクトのデザインシステムを探す**
- 優先順位は プロンプト > プロジェクトのデザインシステム > Claude 自身の選択
- 公式ドキュメントが「繰り返す artifact プロンプトは skill にせよ」と明示している

つまりこの Skill がトークンを定義すれば、組み込み skill はそれを尊重する。**Skill 側で見た目を全部書き下す必要はなく、トークンと構造規則を与えれば足りる**というのが実装方針の芯になる。

## shadcn/ui は使えるか

使えない。Tailwind CSS が必須と明記され、コンポーネントは `.tsx`。ビルド工程を前提とする以上、単一ファイル自己完結という制約と両立しない。

転用するのは視覚語彙だけ — CSS カスタムプロパティによるトークン命名、角丸スケール、中間色の階調。これらは手写しでインライン CSS に落とす。

## いつ開かれるか

**作業中に認知負荷が高くなったとき、あるいは理解が及んでいないと感じたとき**に開く。作業の再開時でも、他人への説明用でもない。

このため、ページの仕事は記録することではなく、**頭に収まらなくなったものを外に出して見えるようにする**こと。ここから3つの帰結が出る。

- **情報は増やすのでなく構造化して減らす。** 網羅は目的ではない。負荷の原因になっているものだけを構造に落とす
- **先頭に来るのは未解決のもの。** 既に片付いたことは後ろでよい
- **読み手は自分なので、前提の説明は要らない。** 背景を知らない読者に向けた導入を書かない

## 起動と更新

**起動は明示的に指示されたときだけ。** 作業が複雑だからといって自分の判断でページを作り始めない。

**起動したあとは、なるべく最新に保つ。** 一度作って放置するのではなく、作業が進むたびに反映する。ただし変更の大きさで扱いを分ける。

| 変更の大きさ | 扱い | 実装 |
| --- | --- | --- |
| 小 — 状態の遷移、行の追加、数値の更新、経緯への1件追加 | 確認を取らず、その場で高頻度に反映する | 既存ファイルの部分編集 |
| 大 — ブロックの追加・削除、構造の変更、全体の書き直し | 要件を固めて確認を取ってから | ページ全体の再出力 |

境界は**部分編集で済むか、全体の再出力が要るか**。再出力はページ全体のトークンを毎回払うので、そこに確認の関門を置く。

## どのユースケースにどの図か

認知負荷の正体はたいてい「**複数のものが、それぞれ違う状態にあって、頭の中で追いきれない**」ことなので、どのユースケースでも状態表が中心に来る。

| ユースケース | 負荷の原因 | 主役の形 | 添える形 |
| --- | --- | --- | --- |
| 障害・不具合の調査 | 仮説が複数あり、どれを潰したか追えない | 仮説の状態表（生存 / 否定 / 未検証 と根拠） | 試したことの時系列 |
| 大きい実装の進行管理 | フェーズが多く、何で止まっているか見えない | 進捗の状態表 | ブロック関係の DAG、残数 |
| 既存システムの把握 | 依存とデータフローが頭に入らない | 有向グラフ | 構成要素の表 |
| 設計の検討・意思決定 | 制約と帰結が連鎖し、選択肢が絡む | 有向グラフ（前提 → 帰結） | 論点表、決定の時系列 |
| 他人の成果物のレビュー | 指摘が散在し、重要度と対応状況が混ざる | 指摘の状態表 | 該当箇所の一覧 |

## ページ内の並び順

読み手は背景を全部知っている一方、**何が未解決かを見失っている**。だから既知から未知へではなく、**未解決から既解決へ**並べる。

1. いま分かっていないこと・次の一手
2. 負荷の原因を解く主役の形
3. そこへ至った経緯（なぜ今の形になっているか）
4. 確定した事項

状態を持つ表も同じで、未解決の行を上に置く。確定した行を上に積むと、いちばん見たいものが下に流れる。

## 出所を辿れるようにする

主張には出所を持たせ、**一次情報があるならリンクにする**。仕事の場面では Slack のメッセージ、設計書、PR の該当箇所、main ブランチ上の実装位置、チケットがこれにあたる。出所を辿れれば情報の価値を評価できるので、「この主張はどれくらい信じてよいか」を読むたびに思い出さずに済む。

**一次情報が無い場合こそ明示する。** リンクが無いものが「まだ調べていない」のか「自分の判断」なのか「根拠の弱い推測」なのか区別できなければ、価値の評価はできない。語彙は5つに閉じる。

| 出所 | 意味 |
| --- | --- |
| リンク | 一次情報がある。クリックで辿れる |
| 実測 | 自分で計測・実行して確かめた |
| 合意 | 関係者と決めた。会話が出所でリンク先は無い |
| 推測 | 根拠が弱く、裏取りが要る |
| — | まだ何も無い |

**状態（解決したか）とは別の軸**なので列を分ける。混ぜると「確定しているが推測に基づく」という最も危ない組み合わせが表現できなくなる。

実装上の注意:

- `<a href>` はページ読み込み時に通信しないので、外部リクエスト 0 の制約に抵触しない。favicon やプレビュー画像を出そうとした時点で抵触するため、**テキストリンクに限る**
- ラベルは短くする（`PR #123`、`設計書`、`SRE-4821`）。URL をそのまま貼ると認知負荷を上げる側に働く
- コード位置は**コミット SHA を固定した permalink** にする。ブランチ相対のリンクは行がずれて別の場所を指すようになる
- 社内のリンクは配布先によっては開けないが、出所があったという事実自体は残る

## 形の判定軸

ユースケースから直接引けないときは、**読み手がそこから何を取り出すか**で選ぶ。

| 取り出すもの | 形 | 実装 |
| --- | --- | --- |
| 順序 — いつ何が起きたか | 線形タイムライン | CSS grid、ドットは擬似要素 |
| 全体の現在値 | 数値の一覧 | レールに縦積み、または grid のタイル。`tabular-nums` |
| 個々の状態 | 状態表 + チップ | `table`。状態は記号・語・色の3重で示し、色だけに載せない |
| 関係・依存 | 有向グラフ | SVG。座標は dagre が計算し、描画は自前（下記） |
| 量の比較 | チャート | 素の JS で描く（下記）。色や形の規約は `dataviz` skill に従う |

チャートだけはまだ実物が無い。他の4つはサンプルで描いてある。

## 集合の重なり

**既定は表。** 何がどの分類に属するかは、行 = 要素・列 = 分類のマトリクスで書く。ベン図は型の一覧に入れず、**表では分かりにくいと言われたときだけ**の特別対応にとどめる。自分から提案しない。

3集合で並べて比べたところ、速さは問いによって割れた。要素や属性を1つ指して引く問い（「レビューはどの図を使う？」「有向グラフを使う場面は？」）は表が速く、重なりや存在しない組み合わせを問う問い（「両方使うのは？」「使わない場面はある？」）はベン図が速い。それでも既定を表に置くのは次の2点による。

- **ベン図が勝つ問いは一度分かれば済む。** 「状態表を使わない場面は無い」と分かればその図の役目は終わる。作業中に繰り返し引くのは要素起点の問いのほう
- **要素が増えるとベン図だけが壊れる。** 表は行が伸びるだけだが、ベン図は領域に文字が入りきらなくなる。1領域2件で改行が要り、3〜4件で破綻する

使うことになった場合の制約:

- **3集合まで。** 4集合は 16 通りの領域が要るのに円 4 つでは 14 通りしか作れず、対角どうしだけが重なる領域が存在しない。楕円で描くと面積と重なりの直感が壊れる
- **ラベル位置は手作業。** 円の配置は固定でよいが、各領域のどこに文字を置くかは自動化できない。領域の重心を計算して配置する（実際、最初の描画ではラベルが隣の領域へはみ出した）

## 図のレイアウト

**座標計算は dagre に任せ、描画は自前の SVG で行う。** ライブラリが返すのはノードの座標とエッジの折れ線だけなので、色・書体・線の太さはページ側の CSS 変数がそのまま効き、意匠は変わらない。

当初は「レイアウトエンジンが無いので層状に並ぶ依存しか描けない」という制約を置いていたが、これは実測せずに決めたものだった。外部リクエスト 0 という制約は CDN を禁じるだけで、**ライブラリをインラインに埋め込めば満たせる**。

| 項目 | 実測値 |
| --- | --- |
| `@dagrejs/dagre` 3.0.0 | 39 KB（依存は `@dagrejs/graphlib` のみ） |
| ライセンスヘッダ | 1.3 KB |
| 18 ノード・18 エッジのページ全体 | 47 KB |

**ライブラリはトークンを消費しない。** ファイルを結合して埋め込むだけなので、97,200 バイトのコードが会話を通ることはない。図の記述として書くのはノードとエッジの配列だけ。

**ライセンス。** dagre・graphlib とも MIT（Chris Pettitt, 2012-2014）で再配布できるが、条件として著作権表示とライセンス全文を複製物に含める必要がある。v3 は minify の際にライセンス表示が落ちているので、**生成する HTML の冒頭にヘッダとして自分で付ける**。v1 系は BSD-3-Clause の文言も抱えているため使わない。本体と LICENSE は `configs/claude/skills/work-map/lib/` に同梱し、skill と寿命を揃える。

mermaid も同じ方法で埋め込めることは確認したが採らない。3.5 MB と 90 倍近い上に、描画までライブラリが行うのでノード幅が不揃いになり、状態の色分けが消える。認知負荷を下げるために状態を見分けさせたいので、意匠の制御を手放す取引が割に合わない。

## チャート

**ライブラリを使わず素の JS で描く。** 46 点の時系列を、スケール変換・目盛りの丸め・ラベルの間引き・面と線のパス生成まで含めて **74 行**で描けることを実測した。

依存グラフとは必要な計算が違う。グラフのレイアウトは交差を減らす最適化問題で自前は非現実的だが、チャートの座標変換は値域をピクセル域へ写す線形写像で、書ける。dagre を入れた必然性はチャートには無い。

必要になったら `d3-scale`（15 KB・ISC）を足す。判断点は**目盛り生成が込み入る要求**が出たとき — 対数軸、時間軸の自動目盛り、積み上げなど。描画まで行う uPlot や Chart.js は採らない。canvas に描くので SVG の意匠と別世界になる。

自前の代償は境界のバグを踏むこと。実際、最初の実装は目盛りの上限が最大値を超えず、ピークが枠外に出ていた（`max 17` に対し `top 15`）。`d3-scale` の `nice()` が正しく扱う部分にあたる。**目盛りを書いたら値の範囲で検算する**手順を持たせる。

**そもそもチャートが要るのは、数値を並べただけでは形が見えないときだけ。** 2 個なら文中に書けばよく、3〜5 個の比較は表で足りる。点数の多い時系列と分布だけがチャートに値する。

| 場面 | チャートに値する量 | 形 |
| --- | --- | --- |
| 障害・不具合の調査 | エラー数 × 時刻、リリース時刻との重ね合わせ、影響範囲の分布 | 時系列 / 横棒 |
| 大きい実装の進行管理 | 残タスク数の推移、フェーズ別の所要日数 | 時系列 / 横棒 |
| 既存システムの把握 | モジュール別の変更頻度・行数、依存の本数分布 | 横棒 |
| 設計の検討・意思決定 | 選択肢ごとのコスト比較（点数が多いときのみ） | 横棒 |
| 他人の成果物のレビュー | 重要度別の指摘件数、ファイル別の指摘密度 | 横棒 |

時系列が要るのは上2つだけで、残りは横棒に落ちる。

## デザイントークン

サンプル（`~/Claude/scratch/html-summary-skill.html`）で確定した値。

- **地** — 藍に寄せたニュートラル `#f3f5f3`。純グレーを避け、アクセント側へわずかに寄せる
- **文字は3段** — 見出し `#141a1c`（比 16.05）／本文 `#33403f`（9.85）／ラベル `#667073`（4.64）。本文を薄い灰色に置くと見出しとの差が開きすぎて弱く見えるので、地との差はしっかり取り、階調は見出しとラベルの側で作る
- **アクセント** — 藍鉄 `#186a83`。1色のみ
- **状態色** — good / warn / serious の3段をアクセントとは別系統に予約し、系列色として使い回さない。critical は当初4段目として置いたが、この用途に該当する実データが無く未使用のまま残ったので外した
- **未確定の表現** — 色ではなく**破線**という形で示す（色覚に依存させない）。状態チップも記号・語・色の3重で示す
- **書体** — 見出しに明朝、本文にゴシック、ID・数値・ラベルに等幅の3役
- **単一テーマ（ライト固定）** — ダークテーマも `prefers-color-scheme` の追従も持たない。作業中に読むだけのページに2組のトークンは要らず、定義が4ブロックから1ブロックに減るぶん更新ごとの再出力も軽くなる

## レイアウト

**行長の制限は本文にだけ掛ける。** 読み物の1行は 40rem 程度で頭打ちにするが、図・表・タイムラインは画面の広さをそのまま使う。ページ全体を1つの狭いカラムに収める作りは、ワイドディスプレイで画面の3分の1しか使わない。

骨格は左に固定レール、右に本体の2カラム。レールには**その時点の状態カウント・セクション目次・更新日**を置く。スクロールしても現在地が見えるので、本体側に同じ数値を再掲しない（重複は更新のたび2箇所を直す羽目になる）。本体の先頭は「次の一手」を1つだけ。

画面幅が 64rem を切ったらレールは上へ畳み、カウントと目次を横並びにする。

**コントラスト比の検証を手順に含める。** ラベル類は 0.7rem（約 11px）と小さく、WCAG の 4.5:1 を満たす必要がある。実際、最初に置いた `--ink-3` は 3.37 で不合格だった（目視では気づけない）。`#667073` へ修正して 4.64 を確認済み。トークンを変えたら計算し直す。

## 未確定の論点

1. **同梱ライブラリの更新** — dagre v3.0.0 をバージョン固定で抱えるので、不具合や脆弱性が出ても自動では上がらない。更新の契機を決めていない
